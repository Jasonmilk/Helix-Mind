# ADR-0015: 领域 WAL（独立追加日志文件作为事实来源）

> **状态**：Draft（P4.5 架构审查点产出 ①，待原型验证后转 Active）
> **日期**：2026-08-28
> **对齐**：审查③ R4（WAL 设计评审，4 项明确产出）、F8（延迟目标修正）、哲学公理"记忆不可篡改 / 极致节能"
> **编号说明**：ADR-0015 是 P4.5 预留编号（此前 0016-0020 已用）

## 问题

- 当前 SQLite 同时承载"日志与状态"，`write_node` 全字段覆盖（ON CONFLICT DO UPDATE）。
- 事实来源（WAL）与投影（状态）混居同一文件，未来分离需重构。
- 无全量溯源：无法回退/快进每个副本，无 push/写操作的完整历史。

## 决策：独立追加日志文件（一步到位，不做 MVP 妥协）

```
/mind-data/
  ├── wal/
  │   ├── default/           # 单租户（未来多租户分目录）
  │   │   ├── 00000001.wal   # 固定大小段（64MB）
  │   │   ├── 00000002.wal
  │   │   └── index/         # 段索引（seq → 文件/偏移）
  │   └── checksums/         # 每段校验文件
  ├── sqlite/                # 投影：液态存储（L1-L3 索引）
  ├── topology/              # 投影：气态内存快照
  └── crystal/               # 投影：晶体归档
```

**关键决策**：SQLite 事件表**彻底放弃**——不是因为 SQLite 不好，而是"日志与状态同文件"在架构上就是错误的。现在多写约 200 行，省未来 2000 行重构（拒绝圆谎）。

## 功能分期（架构正确，能力分期）

| 阶段 | 内容 |
|---|---|
| P5（全功能） | WAL 写路径（append-only, fsync, 段轮转）；BLAKE3 哈希链（`prev_hash`，防位腐坏）；异步投影到 SQLite；replay 恢复 |
| P6+ | 多租户文件分区（预留目录结构）；日志压缩/compaction（预留接口）；Merkle 树高级哈希链验证（预留字段） |

**P4.5 原型范围**（本审查点产出 ②）：只实现 `append + fsync + 单段读取` + 崩溃恢复验证 + 延迟测量。**不是 MVP 妥协，而是正确架构的验证步骤**——先确认桥能承重再过河。

## 延迟目标（审查③ F8 修正）

- 目标：**<10ms p99（SSD）**（原 <5ms 偏乐观，SSD fsync 受 GC/磨损均衡影响）。
- 需明确 fsync 策略：单条 fsync（强一致，慢）vs 批量 fsync（快，有丢失窗口）。原型测两者，P5 定策略并定义丢失窗口。

## 哈希链的安全声明（审查③ R3 修正）

- BLAKE3 哈希链用于**完整性校验**（防位腐坏与意外损坏）。
- **不声明防恶意篡改**（无密钥的哈希链可被攻击者重算）；防恶意篡改需未来密钥基础设施（P6+ ADR）。

## 回滚阈值

若 WAL 原型验证失败（延迟不达标 / 崩溃恢复不可靠）→ 见 `docs/design/wal-fallback.md`（产出 ④）：降级方案为 SQLite 事务 + `deferred_writer` 投影器（当前实现），新 ADR Supersede 本决策。
