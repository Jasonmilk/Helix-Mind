## 审查意见（2026-08-29，严肃审查通过）

### 总体评价

**设计质量：优秀。** 逻辑闭环、工程优雅、物理事实优先。16 字节固定偏移 PAL 头部的设计与工业界成熟实践（HTTP/2 SETTINGS、TLS 1.3 ContentType、gRPC 5-byte header、CAN bus 仲裁 ID）高度同构。

### 大厂成熟案例映射

| CI-144 v2.0 设计 | 工业界成熟实践 | 同构点 |
|---|---|---|
| **PAL 16 字节固定偏移头部** | HTTP/2 SETTINGS frame | 固定偏移、明文可见、用于协商/路由决策 |
| **明文元数据 + 加密载荷** | TLS 1.3 ContentType | 头部在加密前可见，用于区分帧类型，无需解密 |
| **固定偏移 + 长度前缀** | gRPC 5-byte header（1 压缩标志 + 4 长度） | 固定偏移、无分支判断、硬件友好 |
| **CATASTROPHIC 硬覆盖优先级** | CAN bus 仲裁 ID | 固定偏移优先级、高优先级帧抢占总线、硬件级调度 |
| **Physical-Context-Hash** | ROS 2 DDS RTPS header | 固定偏移元数据、用于消息路由和 QoS 匹配 |
| **固定加密路径（AES-GCM）** | TLS 1.3 0-RTT / 1-RTT | 固定密码套件、无分支判断、硬件加速流水线 |

### 前沿研究支撑

| 研究领域 | 核心发现 | PAL 对应设计 |
|---|---|---|
| **具身智能安全交互** | 实时动作风险判断需要亚毫秒级延迟，解密载荷会引入不可接受的延迟 | 明文 Risk-Level 字段，Tuck 不解密即可决策 |
| **实时系统优先级调度** | 固定优先级抢占调度（FPPS）是工业实时系统的事实标准 | CATASTROPHIC 硬覆盖，优先级高于任何本地策略 |
| **零信任安全架构** | 每次请求都需要验证身份和上下文，不依赖网络位置 | Physical-Context-Hash 锁定传感器上下文，防伪造 |
| **边缘计算节能** | 分支判断打断 CPU 流水线，固定计算路径可利用 SIMD/硬件加速 | 固定 16 字节头部、固定加密路径、截断 SHA-256，无分支判断 |

### 逻辑闭环验证

```
传感器数据 → Physical-Context-Hash（PAH）→ PAL 头部（明文）
                                              ↓
INTENT-7（语义）→ PAL（物理锚定）→ CAPABILITY-13（能力认证）→ BIND-19（传输）→ SECURE（加密）
                                              ↓
                                        Tuck 硬拦截（只读 PAL，不解密载荷）
                                              ↓
                              Risk-Level + Override-Flag → 优先级调度 / 硬覆盖
```

### 必须补充的 6 个点

1. **向后兼容性策略**：v1.0 帧中没有 PAL，v2.0 接收端如何判断是否有 PAL？建议 BIND-19 传输头新增 `PAL-Present` 标志位（1 bit）
2. **PAL-Version 在 BIND-19 头中的具体位置**：需明确使用哪个预留位，或扩展传输头
3. **Override-Flag 的授权机制**：`phys:override` scope 的获取必须经过人类授权或 HSM 签名，Tuck 验证签名
4. **Physical-Context-Hash 的验证流程**：PAH 由传感器驱动生成并签名，Tuck 验证签名，验证失败拒绝帧
5. **测试向量**：v2.0-rc.1 阶段发布测试向量集（至少 20 组），确保互操作性
6. **Reserved 字段的治理规则**：Reserved 位的分配走 RFC 流程，未分配位必须为 0，接收端忽略非零值

### 审查结论

**通过，建议补充 6 个点后进入 Draft v2.0-alpha。**

## 一、升级理由

CI-144 v1.0 缺少"特征"——可被 Tuck 等闸门硬实时读取的、固定偏移的、明文可见的物理安全元数据。

| 缺失的特征 | 后果 |
|---|---|
| 无物理上下文（姿态/临边/模态） | Tuck 无法判断"AI 在做什么类型的动作" |
| 无风险等级 | Tuck 无法判断"这个动作有多危险" |
| 无硬覆盖标识 | 灾难场景下无法无条件放行，可能被策略误拦截 |
| 无可观测的固定偏移头部 | Tuck 必须解密载荷才能做决策，违背"极致节能" |
| 无防篡改的物理上下文哈希 | AI 可能伪造物理上下文，绕过安全拦截 |

**一句话总结**：v1.0 定义了"AI 之间怎么说"，但没有定义"AI 在物理世界中怎么做"。v2.0 要做的，就是补齐"物理世界交互"的特征层。

## 二、核心设计原则

| 原则 | 在 v2.0 中的体现 |
|---|---|
| 极致解耦 | 物理锚定层（PAL）与语义层（INTENT-7）分离；元数据与载荷分离；决策依据与内容分离 |
| 极致节能 | 固定 16 字节头部，无分支判断；二进制优先；明文元数据 + 加密载荷，Tuck 不解密即可决策 |
| 白盒可观测 | PAL 提供"特征"——明文、固定偏移、可被 Tuck 硬实时读取的元数据 |
| 事件驱动（无轮询） | CATASTROPHIC 检测通过事件驱动（硬件中断或软件信号量），禁止轮询 |
| 零信任 | 协议不持有任何主密钥，不设计后门；物理上下文哈希由硬件/传感器签名 |
| 渐进生长 | 协议定义"应当如何"，当前软件实现可模拟，未来硬件实现可落地 |

## 三、新增层级：物理锚定层（Physical Anchor Layer, PAL）

在现有四层结构中，PAL 插入在 BIND-19（传输层）之上、INTENT-7（语义层）之下：

```
旧结构： INTENT-7 → CAPABILITY-13 → BIND-19 → SECURE
新结构： INTENT-7 → 物理锚定层(PAL) → CAPABILITY-13 → BIND-19 → SECURE
```

PAL 的所有字段均为明文、固定偏移、固定长度，即使整个帧被加密，PAL 也在传输层可见。

## 四、PAL 固定头部定义（16 字节 / 128 bits）

| 位偏移 | 长度(bit) | 字段名 | 枚举值 | 说明 |
|---|---|---|---|---|
| 0-1 | 2 | Modality | 0=COGNITIVE, 1=RENDER, 2=EXECUTIVE, 3=SENSOR_FEED | 操作模态 |
| 2-3 | 2 | Risk-Level | 0=LOW, 1=MEDIUM, 2=CRITICAL, 3=CATASTROPHIC | 风险等级 |
| 4-5 | 2 | Body-Stance | 0=SEATED, 1=STANDING, 2=MOVING, 3=UNKNOWN | 本体姿态 |
| 6-7 | 2 | Proximity-Edge | 0=SAFE, 1=WARNING, 2=DANGER, 3=CRITICAL_EDGE | 临边/高危环境 |
| 8 | 1 | Output-Dest | 0=INTERNAL, 1=EXTERNAL | 输出目的地 |
| 9 | 1 | Override-Flag | 0=NORMAL, 1=HARD_OVERRIDE | 硬覆盖标志 |
| 10-15 | 6 | Reserved | 全 0 | 未来扩展 |
| 16-127 | 112 | Physical-Context-Hash | SHA-256 截断 | 传感器数据哈希锁定 |

**位分配验证**：2+2+2+2+1+1+6+112 = 128 bits = 16 字节 ✅

## 五、核心规则（写入协议宪章）

### 规则 1：CATASTROPHIC 硬覆盖

```
IF PAL.Risk-Level == 3 (CATASTROPHIC) 
   AND PAL.Override-Flag == 1
THEN 接收端必须：
   1. 在物理层优先响应（事件驱动，禁止轮询）
   2. 并行通过任何可用通道向人类发送紧急信号
   3. 该帧优先级高于任何本地策略缓存、用户配置或 AI 调度
```

### 规则 2：CATASTROPHIC 审计

每次 CATASTROPHIC 硬覆盖触发时，必须生成不可篡改的审计日志（写入 Tuck CAS），记录触发时间、PAL 内容、传感器上下文。

### 规则 3：不可协商性

CATASTROPHIC 硬覆盖规则是协议的不可协商部分（Non-Negotiable Section）。任何声称"兼容 CI-144"的实现，若违反此规则，即自动丧失兼容性声明资格。

## 六、BIND-19 帧结构升级

```
[ 8字节 BIND-19 传输头 ] + [ 16字节 PAL ] + [ 可变长加密载荷 ]
```

传输头新增字段：PAL-Version（2 bits），指示 PAL 版本（当前 v2.0 = 01）。

**关键约束**：PAL 的偏移量固定，任何实现不得将 PAL 置于加密载荷中。

**待补充**：PAL-Present 标志位（1 bit），用于 v1.0/v2.0 向后兼容协商。

## 七、加密策略（固定路径，无分支判断）

| 原则 | 说明 |
|---|---|
| 非观测模式（生产） | 所有载荷一律 AES-GCM 加密。不设"是否加密"的判断分支，避免额外能耗 |
| 观测模式（调试/审计） | 载荷明文或可选加密，由用户选择 |
| Physical-Context-Hash | 所有 PAH 一律计算（可使用截断 SHA-256，降低 50% 计算量）。固定计算路径，无分支判断 |

**关键洞察**：节能的敌人是分支判断，而不是固定计算。固定路径可利用硬件加速流水线；分支判断打断流水线，产生额外能耗。

## 八、CAPABILITY-13 物理 Scope 扩展

| Scope 名称 | 说明 | 关联 Risk-Level |
|---|---|---|
| phys:low_speed | 允许低速/低扭矩动作 | MEDIUM 及以下 |
| phys:high_speed | 允许高速/高扭矩动作 | CRITICAL 及以上 |
| phys:override | 允许触发 HARD_OVERRIDE | 仅 CATASTROPHIC |
| phys:human_call | 允许并行呼叫人类协助 | 任何 Risk |

**约束**：帧中 CAPABILITY-13 携带的 Scope 列表必须与 PAL 中的 Risk-Level 匹配。若 Scope 不足但 Risk-Level 过高，该帧在协议层面即视为非法。

**待补充**：`phys:override` scope 的获取必须经过人类授权（CAPABILITY-13 签名）或 HSM 签名；Tuck 验证签名，验证失败按普通帧处理。

## 九、非观测模式（二进制传输）

- **观测模式**：PAL 明文可见，载荷可加密或明文，适合调试/审计
- **非观测模式**：PAL 始终明文，载荷强加密（AES-GCM），是具身智能体的强制默认形态
- **二进制形态**：帧为紧凑二进制，最小帧开销 24 字节（8+16），JSON/文本仅用于调试

**关键**：Tuck 在非观测模式下仍可仅凭 PAL 做拦截决策，因为 PAH 从未被加密，且偏移固定。

## 十、当前 Helix-Mind 的软件实现（力所能及）

协议定义"应当如何"，当前实现用软件模拟是合理的渐进路径。

| 协议要求 | Helix-Mind 当前实现 |
|---|---|
| 事件驱动、无轮询 | ✅ tokio::select! 异步等待 |
| CATASTROPHIC 优先级 | ✅ 用 tokio::sync::Notify 实现高优先级通道 |
| PAL 固定偏移解析 | ✅ 代码中固定偏移解析 |
| 硬件中断 | ❌ 当前无法实现（硬件阶段） |

## 十二、一句话总结

CI-144 v2.0 为协议补充了"特征"——16 字节固定偏移的物理锚定头（PAL）。它明文可见、固定加密路径、事件驱动无轮询。锁的接口由协议定义，钥匙由各参与方自行管理。当前软件可模拟，未来硬件可落地。协议先行，渐进生长。
