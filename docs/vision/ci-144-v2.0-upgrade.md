## 一、升级理由

CI-144 v1.0 缺少"特征"——可被 Tuck 等闸门硬实时读取的、固定偏移的、明文可见的物理安全元数据。

| 缺失的特征 | 后果 |
|---|---|
| 无物理上下文（姿态/临边/模态） | Tuck 无法判断"AI 在做什么类型的动作" |
| 无风险等级 | Tuck 无法判断"这个动作有多危险" |
| 无硬覆盖标识 | 灾难场景下无法无条件放行，可能被策略误拦截 |
| 无可观测的固定偏移头部 | Tuck 必须解密载荷才能做决策，违背"极致节能" |
| 无防篡改的物理上下文哈希 | AI 可能伪造物理上下文，绕过安全拦截 |

**一句话总结**：v1.0 定义了"AI 之间怎么说"，但没有定义"AI 在物理世界中怎么做"。v2.0 补齐"物理世界交互"的特征层。

## 二、核心设计原则

| 原则 | 在 v2.0 中的体现 |
|---|---|
| 极致解耦 | 物理锚定层（PAL）与语义层（INTENT-7）分离；元数据与载荷分离 |
| 极致节能 | 固定 24 字节头部，无分支判断；明文元数据 + 加密载荷 |
| 白盒可观测 | PAL 提供明文、固定偏移、可被 Tuck 硬实时读取的元数据 |
| 事件驱动（无轮询） | CATASTROPHIC 检测通过硬件中断或软件信号量，禁止轮询 |
| 零信任 | 协议不持有主密钥；物理上下文由硬件/传感器签名 |
| 渐进生长 | 当前软件可模拟，未来硬件可落地 |

## 三、新增层级：物理锚定层（Physical Anchor Layer, PAL）

插入位置：INTENT-7 → **PAL** → CAPABILITY-13 → BIND-19 → SECURE

PAL 总长度固定为 **24 字节（192 bits）**，全部明文、固定偏移，即使整个帧被加密，PAL 也在传输层可见。

### PAL 固定头部定义（24 字节 / 192 bits）

| 位偏移 | 长度(bit) | 字段名 | 枚举值 / 说明 |
|---|---|---|---|
| 0-1 | 2 | Modality | 0=COGNITIVE, 1=RENDER, 2=EXECUTIVE, 3=SENSOR_FEED |
| 2-3 | 2 | Risk-Level | 0=LOW, 1=MEDIUM, 2=CRITICAL, 3=CATASTROPHIC |
| 4-5 | 2 | Body-Stance | 0=SEATED, 1=STANDING, 2=MOVING, 3=UNKNOWN |
| 6-7 | 2 | Proximity-Edge | 0=SAFE, 1=WARNING, 2=DANGER, 3=CRITICAL_EDGE |
| 8 | 1 | Output-Dest | 0=INTERNAL, 1=EXTERNAL |
| 9 | 1 | Override-Flag | 0=NORMAL, 1=HARD_OVERRIDE |
| 10-13 | 4 | PAL-Version | 当前 v2.0 = 0001（支持最多 16 个版本） |
| 14 | 1 | Replay-Enable | 1=强制检查 BIND-19 序列号；0=降级跳过（需补充安全约束） |
| 15 | 1 | Reserved | 强制为 0（未来扩展） |
| 16-127 | 112 | Physical-Context-Hash | SHA-256 截断（高 112 位） |
| 128-191 | 64 | PAH-Signature | ECC 签名截断（快速校验层，完整验证在载荷解密后） |

**位分配验证**：2+2+2+2+1+1+4+1+1+112+64 = 192 bits = 24 字节 ✅

> ⚠️ **重要变更**：原草案 16 字节 PAL 不具备签名存放空间，现强制扩展至 24 字节。所有实现必须按 24 字节固定偏移解析，不得回退。

## 四、BIND-19 帧结构升级（配合防重放）

新帧结构：

```
[ 8字节 BIND-19 传输头（含 Seq-Counter） ] + [ 24字节 PAL ] + [ 可变长加密载荷 ]
```

BIND-19 传输头必须新增以下字段：

- **PAL-Present（1 bit）**：指示本帧是否包含 PAL（向后兼容）。v2.0 帧必须置 1；v1.0 接收端忽略此位。
- **Seq-Counter（16 bits）**：单调递增序列号（防重放）。发送端原子递增，接收端缓存并查重。
  - 具体位置：复用原 BIND-19 v1.0 头部的第 6-7 字节（原 Reserved 区域）。
  - 初始化：每次冷启动时取随机值，避免重启后序列号重置被攻击者利用。
  - 原子递增：多线程环境下必须使用 `AtomicU16` 配合 `fetch_add(1, Ordering::SeqCst)`，确保严格单调递增，不允许乱序。
  - **回绕与密钥轮换策略（补丁 C，已锁定）**：
    - **回绕检测**：发送端（Helix-Mind）检测到 Seq-Counter 即将溢出（≥ 65534）时，必须在下一帧触发密钥轮换。预留 2 帧缓冲。
    - **轮换流程**：
      1. 发送端生成新的会话加密密钥（AES-GCM 新 Key）。
      2. 发送端发送一个特殊的 `KEY_ROTATION` 控制帧（非 PAL 数据帧），携带新密钥（由主密钥加密保护）。
      3. 接收端（Tuck）确认新密钥后，重置该源 ID 的 Last-Seen-Seq 缓存（允许新序列号从 0 开始）。
      4. 若接收端未收到轮换帧而检测到序列号回绕（突然从 65535 跳到 0），直接视为异常重放攻击，立即拒绝所有帧并触发硬件告警，直到人工复位。
    - **alpha 实现中需明确**：KEY_ROTATION 控制帧格式（BIND-19 新帧类型 or INTENT-7 新动词）、轮换期间帧处理（旧密钥 or 新密钥）、主密钥管理与轮换周期。

## 五、核心规则（协议宪章）

### 规则 1：CATASTROPHIC 硬覆盖

```
IF PAL.Risk-Level == 3 (CATASTROPHIC) AND PAL.Override-Flag == 1
THEN 接收端必须：
  1. 物理层优先响应（事件驱动，禁止轮询）
  2. 并行通过任何可用通道向人类发送紧急信号
  3. 优先级高于任何本地策略缓存、用户配置或 AI 调度
```

### 规则 2：CATASTROPHIC 审计

每次触发必须生成不可篡改的审计日志，记录触发时间、PAL 内容、传感器上下文、BIND-19 序列号。

### 规则 3：不可协商性

违反者自动丧失兼容性声明资格。

## 六、新增强制性安全规程

### 规则 4：防重放检查

- 若 PAL.Replay-Enable == 1，Tuck 必须校验 BIND-19.Seq-Counter。
- 拒绝条件：Seq-Counter ≤ Last-Seen-Seq[Source-ID]。
- 拒绝动作：拉高 ERROR 电平，写入审计日志 REJECTED_REPLAY，严禁放行。
- 缓存容量：至少缓存 1024 个源，每源保留最后 256 个序列号。

**Replay-Enable=0 强化约束（补丁 A，已锁定，零信任补丁）**：

原缺陷：若攻击者将第 14 位置 0，则防重放机制被静默关闭，可无限重放旧帧。

当 Tuck 解析到 PAL.Replay-Enable == 0 时，必须同时执行以下三条硬约束，缺一不可：

1. **风险降级**：无论 PAL.Risk-Level 原始值为何，Tuck 内部决策时强制视为 MEDIUM（等级 1）。这意味着永远无法触发 CATASTROPHIC 硬覆盖，从根本上杜绝利用重放发动高危物理攻击。
2. **强化验证**：必须强制通过 PAH-Signature 验证（规则 5）。用防伪强度弥补防重放缺失，若签名验证失败，直接拒绝帧。
3. **审计强制标记**：审计日志必须显式记录 "REPLAY_DISABLED" 事件，且该条日志必须附带当前硬件时钟（防止攻击者覆盖时间戳）。

**代码级约束（已修正语义：直接强制 MEDIUM，不使用 min）**：

```rust
if pal.replay_enable() == 0 {
    // 降级模式强制安全策略：无论原始值为何，强制视为 MEDIUM
    let effective_risk = RiskLevel::MEDIUM;
    if !verify_pah_signature(&pal) {
        return Decision::Reject;
    }
    write_audit("REPLAY_DISABLED", effective_risk, hardware_clock());
    // 后续决策仅使用 effective_risk，丢弃原始高优先级
}
```

- 默认值为 1（强制检查），只有明确授权的场景才能设为 0。

### 规则 5：PAH 强制验证

**PAH-Signature 双层安全架构（补丁 B，已锁定）**：

原缺陷：64-bit 截断签名理论上存在伪造可能（生日攻击约 2^32），无法作为唯一身份认证。

正式定义（双层模型）：

- **第一层（快速校验层，Tuck 硬实时）**：使用 64-bit ECC 截断签名。此层仅用于 Tuck 的亚毫秒级拦截决策，提供基础防伪，抵抗偶发噪声或简单篡改。
- **第二层（完整验证层，Helix-Mind/云端审计）**：所有具身帧在载荷（加密或明文）中必须附带完整的 512-bit ECC 签名（如 Ed25519 全量签名）。该签名在载荷解密后由 Anaphase 或云端安全审计模块验证。
- **逻辑闭环**：即便第一层 64-bit 被暴力碰撞（概率极低且需大量算力），第二层完整验证会在事后立刻发现并触发全局告警和密钥吊销机制。两者组合构成"实时拦截 + 事后追责"的安全闭环。
- **alpha 实现中需明确**：第二层 512-bit 签名在载荷中的具体位置（载荷头部 or 扩展字段）、第二层验证失败的处理流程（拒绝帧 or 标记可疑+告警）、密钥吊销机制（触发者/传播方式/生效时间）。

**第一层快速校验执行规则**：

- Tuck 必须在决策前用内置公钥验证 PAH-Signature（快速校验层，64-bit）。
- 验证失败：拒绝帧 + ERROR 电平 + 声光告警，写入审计 PAH_FAIL。
- **双层安全**：64-bit PAH-Signature 是快速校验层（用于 Tuck 硬实时决策）；完整 512-bit ECC 签名验证在载荷解密后进行（待补充到实现规范）。
- 唯一例外（降级模式）：仅当 Tuck 电量 < 5% 或硬件加速器故障时，允许跳过验证，但必须强制将所有帧的 Risk-Level 视为 MEDIUM，并在审计日志标记 PAH_SKIP_LOW_POWER。
- 降级模式必须由物理拨码开关或硬件寄存器启用，严禁软件动态切换。

## 七、加密策略

| 原则 | 说明 |
|---|---|
| 非观测模式（生产） | 所有载荷一律 AES-GCM 加密，无"是否加密"分支 |
| 观测模式（调试） | 载荷明文或可选加密，由用户选择 |
| Physical-Context-Hash | 固定计算截断 SHA-256，无分支判断 |

## 八、CAPABILITY-13 物理 Scope 扩展

| Scope 名称 | 说明 | 关联 Risk-Level |
|---|---|---|
| phys:low_speed | 允许低速/低扭矩动作 | MEDIUM 及以下 |
| phys:high_speed | 允许高速/高扭矩动作 | CRITICAL 及以上 |
| phys:override | 允许触发 HARD_OVERRIDE | 仅 CATASTROPHIC，且必须经人类授权或 HSM 签名 |
| phys:human_call | 允许并行呼叫人类协助 | 任何 Risk |

**phys:override 约束**：phys:override scope 不得由 AI 自主声明，必须由外部人类操作员授权或硬件安全模块（HSM）签发，Tuck 验证签名。

## 九、向前兼容性与 Reserved 治理

- **向后兼容**：v2.0 发送端必须在 BIND-19 头中置 PAL-Present=1。v1.0 接收端忽略该标志及后续字节，仍可处理载荷（但无法利用 PAL）。v2.0 接收端若收到 PAL-Present=0，视为 v1.0 遗留帧，按旧逻辑处理。
- **Reserved 治理**：PAL 第 15 位目前强制为 0。未来任何使用该位的扩展，必须提交正式 ADR 并经协议委员会审查分配，未分配前接收端必须忽略此位（向前兼容）。
