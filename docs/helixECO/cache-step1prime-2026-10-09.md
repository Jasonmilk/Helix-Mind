## 三、同一份数据暴露了**真正的顺序**（本轮最有价值的发现）

```
a[76…] = 'kens]\nuser message at 2026-10-09 04:15:21 +0800\nnow: … +0800\n\n第 20 轮…'
                                                                                  ↑
                                    （骨架 '[conversation so far — one line per round' 在**更后面**）
```

⇒ **实际顺序：`稳定头(~76B)` → `时间锚` → `本轮用户消息` → `骨架`**

### ⇒ 我的"分块（把骨架前置）"方案**是错的**

骨架**本来就在最后**。把它**前移** = 把**滑动**的块搬到**更靠前** ⇒ **断裂更早，缓存更差。**

> **人类是对的（第二十三条）：骨架是滑动窗口（删头 + 追加），与前缀缓存天然相冲。**
> 而它比时间锚**重要得多**：时间锚只毁掉它之后；**骨架滑动毁掉"从删掉那一行起"的全部**。
> 且链条一到第 13 轮（`max_lines=12`）就进入滑动区 ⇒ 21 轮里大部分时间在里面 ⇒ 平均个位数命中。

## 四、gist 是**对的**（已核实）

```rust
let mut gist = String::new();
… gist.push_str(piece);            // 只追加
```
⇒ **gist 块是追加式**（`<period_id>.gist` write-once 侧车 + 拼接）。
**它不是滑动源。滑动源是"最近 N 行"那个窗口。**

## 五、因此下一步的**正确**实验（不是移块，是四种正交改动各测一次）

| 实验 | 改动 | 预期 |
|---|---|---|
| **A** | 只把**时间锚**后置（移到本轮消息之后） | 把 10% 推到更远 |
| **B** | 骨架由"最近 N 行滑动"改为**只追加**（放弃窗口，用 gist 承担压缩） | **最可能的大头** |
| **C** | 增大 `max_lines` 使滑动推迟（治标） | 延迟断裂 |
| **D** | 加 `--cache-reuse 256`（滑动窗口恰恰**制造**"公共前缀之后的可复用块"，故可能对症） | 复用旧骨架残块 |

**每个都要单独报 `cached/prompt`**，且**必须带语义回归**（第 20 条）：
```
① cached_tokens / prompt_tokens   改前 vs 改后
② 21 轮 gist 判据仍绿
```
**成功判据写"从 5% 显著提升"，不写"接近 99.6%"** —— 99.6% 是"同一 prompt"的上限，不是真实可达值。
