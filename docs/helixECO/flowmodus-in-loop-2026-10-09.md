## 〇、🔴 事故记录（我造成，已恢复，**如实记**）

我按人类给的脚本跑了变异，命令里包含 `up --restart`。**该调用超 15 分钟被系统取消**，
而 **`up` 是前台进程**（它自己打印"按 Ctrl+C 停止面板"）⇒ **我的调用被杀时，把它的子进程一并带走**。

```
事故后实测：60053 ❌ 60054 ❌ 50050 ❌ 50061 ❌ 8080 ✅（只有 llama-server 活着）
恢复：nohup ./target/debug/up --restart &  ⇒ 60052/60053/60054/50050/50052/50061 全部回来
```

**⇒ 教训**：`up` 是**前台监督者**，**不得**在有超时风险的调用里直接运行；必须 `nohup … &` 分离。
（我的两次错误：① 同一条命令里既做变异又做恢复，② 用前台方式启动监督进程。）

## 一、FlowModus 架构测绘（人类的主问题）

```
FlowModus/
  pyproject.toml · uv.lock · src/flowmodus/   ← Python 实现（39 个 .py）
  flowmodus-rs/  Cargo.toml  name = "flowmodus"  ← Rust 重写（28 个 .rs）
  schemas/ · tools/ · tests/ · docs/
```

**⇒ 确实是双实现并存**（人类怀疑成立）。**但运行时只有一个在跑**：

```
60053  flowmodus pid=61415     ┐
60054  flowmodus pid=61427     ┘ 进程名 = crate 名 ⇒ **跑的是 Rust 版**
8080   llama-swa  pid=90117      llama.cpp 的推理服务（在 ports.json 的 not_ecosystem 表上）
```

**⇒ 结论：Rust 版是活的，Python 版是遗留/参考。** 这就是"混在一起"的实际形态 ——
**不是运行时混，是仓库里两份实现共存，而判据（进程名 = crate 名）恰好能分开。**


**⇒ 前置 grep（人类建议的便宜做法）结果：`config.toml` 里没有第二个模型端点；
`src/**` 与 `Cellrix/web/assets` 里没有 `:8080` 直连。**
**⇒ 前置检查是"干净"的 —— 但它定不了案（人类也说它只能"若出现则已定"，反向不成立）。**

## 四、变异（人类脚本）：**做了，但我的设计有缺陷 ⇒ 不构成结论**

```
① 60054 在听 → kill 之
② 面板 API 发一句话 → {"error":"Connection refused (os error 61)"}
```

**按人类的判据，「报错」= GREEN（FlowModus 确实在路由）。**

**🔴 但对照缺失，我不把它当结论**：
1. 我用的 `job_id` 是**编造的**（`run-0000…`）⇒ 面板可能**因这个**而报错，与变异无关；
2. **没先打基线**（60054 活着时用同一个 job_id 打一次）⇒ 无法分辨 `Connection refused` 来自
   **anaphase→60054** 还是 **面板→anaphase**。

**⇒ 结论：证据偏向"在环"（GREEN），但对照缺失 ⇒ 未定案。**
**正确的重测**（下次，5 分钟）：同一个**真实 period_id** 打两次 —— 60054 活着一次（期望成功）、
停掉一次（期望报错）；**两次的差异**才是证据。

## 六、新纪律入册

**第二十四条 · 存活 ≠ 在环。**
「已就绪」是**端口**的属性，不是**能力**的属性（与"mtime 是签出的属性"同族）。
判据：**把组件停掉，看有没有东西变化。没有变化 ⇒ 它不在路径上。**
**补充判据（本轮事故换来的）**：变异必须**有对照** —— 同一输入在"活着/停掉"两种状态下各跑一次，
**两次的差异**才是证据。只跑"停掉"那一次，得到的是"报错"，不是"它在环"。

**第二十五条 · 组件 A 的功能被观测到，证明不了是 A 做的。**
必要非充分：必须排除绕过路径。

**第二十六条（新，本轮事故）· 前台监督进程不得放在有超时风险的调用里。**
`up` 会打印"按 Ctrl+C 停止面板" —— 它**是**前台监督者；调用被杀 ⇒ 它的子进程一并死亡。
**必须 `nohup … &` 分离启动**，否则一次超时就会把整个栈带走。
