> **形态说明（人类 2026-10-10）**：*"最好的形态应该是指派完成某些工作，而不是过分明确的任务 ——
> 比如去修复某个项目里的'红'，如果遇到跨项目需要停止，并报告。"*
> **⇒ 本卡只给：目标 · 边界 · 自证 · 报告格式 · 停手条件。不给步骤。**

```
【指派】让 FlowModus 的 CI 变绿。

【背景（一句）】它的 CI 是新建的（此前没有 CI），**首次 run 就红**；而本地
`cd flowmodus-rs && cargo test --all-features` 是**绿的** ⇒ 所以这属于"本地绿 / CI 红"的环境差异类。
同类的两种成因我已在别处见过：**缺系统依赖**（`protoc`，我加过一次）· **YAML 非法**（症状是"没有 job"）。

【你的边界（硬线）】
1. **只改 FlowModus 仓内**的东西（代码 / 配置 / CI / 文档）。
2. **跨仓需求 ⇒ 停手并报告** —— 不要去改别的仓，也不要改 phyt-DNA 的引擎；
   需要别的仓配合，就在报告里写明"需要 <仓> 的 <什么改动>"。
3. **不许把红藏起来**：不得删测试 / skip / 放宽判据 / 把失败降级成 warning。**红只能被真正修好。**
4. CI 失败详情：**job summary 是公开可读的**（网页直接看）。artifact 下载需凭据（**你大概拿不到**）
   ⇒ 拿不到就**本地复现**，不要猜。

【自证（必做，原样贴输出）】
· 本地等价命令：`cd flowmodus-rs && cargo test --all-features`（**这就是 CI 的硬门**）
· 若你改了 workflow：**先在本地解析 YAML**（否则"配置层静默"：坏 YAML 不报错，只是没有 job）

【报告格式】
① **根因**（一句；**没找到就明说"未找到"，并给出你排除掉的假设与依据** —— 别编一个）
② **改了什么**（文件 + 为什么）
③ **自证**：命令 + **原样输出**
④ **【异常标记】**：你在过程里看到任何"意外特征"（可疑输出 / 文档与实现不符 / 需要跨仓）
   ⇒ **如实上报，不要顺手处理**（你的眼睛是击发时最便宜的审计）

【停手条件（任一即停，不要越界）】
· 根因找到但修复需要**跨仓** · 需要动 **phyt-DNA / anaphase / Cellrix / helix-mind / Tuck** ·
· 发现"红其实是** CI 自身**的问题" ⇒ **可以修 CI**，但报告里必须说明这一点（并附证据）。
```
